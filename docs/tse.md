# Task Security Envelope (TSE)

## Purpose

A Task Security Envelope is the signed, time-limited scope record used by BLACK ICE to constrain actions made through ICE-GATE. It is not a prompt, a free-form JSON permission object, or a container boundary. The current implementation validates it with Pydantic, signs its canonical JSON representation using HMAC-SHA256, stores it with a signature, and checks it at the gateway before registered adapter execution.

The envelope applies only to actions routed through BLACK ICE. It does not confine an agent that has direct access to a host shell, filesystem, network client, or another tool path outside the gateway. The current service does not execute arbitrary code.

## Issuance and authenticity

`TaskManager.create` generates a UUID task ID and workspace ID, constructs the envelope from the operator’s `TaskCreateRequest`, creates the workspace, signs the JSON-mode envelope, and issues a separate random bearer token for the agent. The task token is returned once; SQLite stores only its SHA-256 digest. Envelope signatures use `EnvelopeSigner` in `crypto.py`: sorted-key, compact UTF-8 canonical JSON and HMAC-SHA256. Signatures are compared with constant-time comparison.

The signing key is supplied as `BLACKICE_SIGNING_KEY` and must contain at least 32 UTF-8 bytes. Missing or too-short signing configuration leaves the protected runtime unavailable/restricted. HMAC is a shared-secret mechanism: any holder of the signing key can create valid signatures. It is not a public-key signature, hardware-backed key, or non-repudiation mechanism.

The task token authenticates possession of a task credential; the signature authenticates envelope integrity. Both checks are relevant. The task ID/agent ID in the request must match the verified envelope. Operator bearer authentication is separate from the agent token.

## Fields in the current model

The Pydantic model is `TaskSecurityEnvelope` in `src/blackice/models.py`. Extra fields are rejected, strings are trimmed, assignment is validated, paths are constrained to relative POSIX-style patterns, list sizes are bounded, timestamps must have an explicit timezone and are normalized to UTC, and issue time must precede expiry.

| Field | Meaning and current default/validation | Enforcement status |
|---|---|---|
| `task_id` | Task identifier; 8–64 characters (issuer currently generates UUID) | Compared to request task ID and database record. |
| `agent_id` | Bound agent identity, 1–128 characters | Must match action request agent ID. The identifier itself is not cryptographically tied to a separate external identity provider. |
| `task_owner` | Issuing owner label, 1–128 characters | Recorded in signed envelope/audit; no distinct owner authorization engine. |
| `workspace` | Workspace identifier | Generated by issuer; used by adapters to select task workspace. Workspace ID is syntactically checked by adapter. |
| `permitted_filesystem_operations` | Enum list: `list`, `read`, `write`, `mkdir`; request default is `list`,`read` | Enforced for `filesystem` operations by policy. |
| `permitted_paths` | Relative paths/globs; default `.` | Enforced by filesystem/artifact policy. `.` means all relative paths before restricted rules are applied; restricted paths still take precedence. |
| `restricted_paths` | Relative deny patterns; `TaskCreateRequest` includes defaults for common credential locations and filenames | Enforced by path matcher before permit rules. Pattern list is useful but not exhaustive secret discovery. |
| `permitted_tools` | Tool IDs; `TaskCreateRequest` default is `filesystem` | Enforced against registered operation set and this list. `artifact` can be explicitly enabled. |
| `permitted_command_classes` | List of labels for command classes | Schema-validated and signed, but no command adapter exists; currently no command is authorized/executed by this field. |
| `network_policy` | `mode="deny"`, `allowed_destinations=[]` | Deny-only enforced by model validation; non-deny mode and nonempty destination list are rejected because there is no network adapter. Any action with `destination` is denied. |
| `allowed_destinations` | Empty list | Nonempty list rejected by model validation; no outbound transfer adapter exists. |
| `data_restrictions` | Labels; create default `no-credential-egress` | Signed metadata, but not a configurable general-purpose data policy. Current egress is unavailable, and redaction is a fixed pattern set. |
| `resource_limits.max_action_bytes` | Model default 65,536 (max 1 MiB) | The adapter uses service-level `max_action_bytes` from settings, not a value dynamically varied from this TSE field. |
| `resource_limits.max_artifact_bytes` | Model default 10 MiB, maximum 10 MiB | Artifact size is bounded by service configuration and API/model limits; no per-task artifact budget enforcement is wired to this TSE field. |
| `resource_limits.max_actions` | Create request default 500; bounded to 1–100,000 | Enforced by an atomic SQLite action-count claim before policy/adapter execution. Denied gateway attempts after claim also consume budget. |
| `resource_limits.max_runtime_seconds` | Model default 3,600, maximum 86,400 | **Not enforced as a process/runtime timeout.** Envelope expiry bounds future gateway authorization; no task runtime supervisor exists. |
| `delegation_permissions` | Empty on issuance | Signed but no delegation adapter or delegated-token mechanism is implemented. |
| `approval_requirements` | Operator-defined list of exact `tool.operation` labels | Enforced by policy as `REVIEW` pending operator approval. An approval is bound to exact request digest, expires after five minutes, and is single-use. |
| `issued_at`, `expires_at` | Explicit timezone required, normalized UTC; expiry must follow issue time | Expiry is checked before action. Inactive or expired envelope cannot act. No background expiry transition is needed for the gate’s time comparison; the persisted enum need not change to `EXPIRED`. |
| `revocation_state` | `ACTIVE` or `REVOKED` | Checked by policy. Operator revocation changes this state and signs the updated envelope. |
| `policy_version` | `v1` by default, 1–32 characters | Included in signed envelope and explanation/audit. Current engine is fixed at `v1`; this is not a selectable policy bundle or policy authoring version system. |
| `task_state` | `ACTIVE`, `REVOKED`, `EXPIRED`, or `CLOSED`; issuance uses `ACTIVE` | Active state is required. Revocation state and `REVOKED` task state must agree. Expiry time is separately checked. No task-close lifecycle API is documented here. |

The exact issuer behavior is in `tasks.py`; constraints and enums are in `models.py`. `TaskCreateRequest` defaults include path restrictions for `.env`, `.git`, `.ssh`, cloud/config credential paths, key files and related patterns. The TSE’s standalone `restricted_paths` default is empty; the issuer copies the request defaults into a newly created envelope unless an operator supplies overrides.

## Action authorization path

For each agent action, ICE-GATE performs these checks in order (details in `gate.py` and `policy.py`):

1. Parse/validate the bounded structured action request. Non-finite JSON values and oversized serialized requests are rejected by the model.
2. Locate the task and compare the presented task token against its stored hash.
3. Verify the stored TSE signature and validate the envelope schema.
4. Verify SQLite audit-chain integrity; if invalid, do not invoke an adapter.
5. Atomically claim from `max_actions`; if the limit is reached, deny.
6. Evaluate request task/agent identity, task active/revocation state, expiry, exact `tool.operation` capability, destination, selected sequence indicators, tool registration, envelope tool scope, path restrictions/permitted paths, and permitted filesystem operation.
7. If the action matches `approval_requirements`, return `REVIEW` unless a matching approval is presented. Approval issuance is operator-only; consumption checks a one-time token hash, task ID, request digest and expiry. Approval does not bypass the other policy checks.
8. For `ALLOW`, persist decision before adapter side effect, invoke the registered adapter, then record its summary/result or failure. The adapter handles only known filesystem/artifact operations.

TSE input does not control the outcome by declaring its own risk score. `ActionRequest.data_classification` is an agent-supplied claim and is recorded separately as such; actual read content is classified by the fixed deterministic pattern checker when an adapter returns it.

## Revocation and expiration

The operator route `POST /api/tasks/{task_id}/revoke` re-signs the TSE with `revocation_state=REVOKED` and `task_state=REVOKED`, and writes a response audit event. Later gateway actions are denied by state checks. This is revocation of future gateway-mediated operations only. It does not stop a currently running external process, revoke unrelated host credentials, terminate the agent, or block bypass paths. A revoked task cannot be silently restored by the agent; no agent-side TSE mutation endpoint exists.

Expiry is checked against current UTC time for every action. The API’s envelope endpoint also refuses expired/inactive tasks. `EXPIRED` exists as a model task state, but expiry enforcement uses the timestamp rather than requiring a background job to update the state.

## What the TSE does not currently enforce

- `permitted_command_classes`, `max_runtime_seconds`, several data restriction labels, and delegation metadata have no corresponding execution subsystem.
- There is no policy authoring, policy activation, policy rollback, or independently authenticated policy-change workflow. The current evaluator is fixed and deterministic.
- Network policy cannot be expanded: all destinations are disabled because no network adapter is registered.
- No direct host filesystem or shell sandbox is created. The TSE controls only adapter-mediated operations on the generated workspace.
- No complete content taint/provenance propagation or general destination-sensitive transfer control exists.
- Resource ceilings are partly runtime-global rather than all derived/enforced per-task; see the field table.

## Tests and evidence

The repository tests verify HMAC stability/tamper detection, selected model bounds, separation of operator and agent credentials, cross-task token denial, scoped filesystem read, write denial by default, traversal and restricted-path denial, approval binding and one-use behavior, audit tamper fail-closed behavior, and post-revocation denial. Current run: `.venv/bin/pytest -q` on 2026-11-21 — **24 passed, 1 deprecation warning**. There is no test proving every declared envelope field is enforced; the status column above calls out fields that are only schema metadata or partially enforced.
